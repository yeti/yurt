# Infrastructure-as-Code

Terraform configurations for __YURT_PROJECT_NAME__'s cloud providers. Each
provider lives under its own directory, and **state is separated per provider
per environment** — every `environments/<env>` directory is its own root module
with its own HCP Terraform workspace.

- [`auth0/`](./auth0) — Auth0 tenants, applications, APIs, and connections
- [`render/`](./render) — Render web services, static sites, and Postgres

State and locking are managed in **HCP Terraform** (org `__YURT_HCP_ORG__`).
Workspaces run in **Local execution** mode, so Terraform runs in GitHub Actions
(or locally via direnv), and HCP holds state only.

| Root module | HCP workspace |
| --- | --- |
| `auth0/environments/staging` | `__YURT_PROJECT_SLUG__-auth0-staging` |
| `auth0/environments/production` | `__YURT_PROJECT_SLUG__-auth0-production` |
| `render/environments/staging` | `__YURT_PROJECT_SLUG__-render-staging` |
| `render/environments/production` | `__YURT_PROJECT_SLUG__-render-production` |
| `render/project` | `__YURT_PROJECT_SLUG__-render-project` |

`render/project` is the owner-level root module: it creates the Render project
and its environments, minting the `evm-…` environment IDs that each
`render/environments/<env>` root module references (hand-copied, no
cross-workspace data source). Apply it first — both on first-time setup and
whenever an environment is added.

> **Generated by yurt.** Most project-specific values (HCP org, workspace
> names, repo URL, API identifier, database names) were filled in when this
> repo was generated. The values that can only exist after resources are
> created ship as `REPLACE_ME` placeholders — [First-time setup](#first-time-setup)
> walks through pinning each one. `grep -rn "REPLACE_ME" infra/` lists what's
> still outstanding.

## Local Setup (macOS)

One-time onboarding, applies to every provider directory.

1. Install the tooling:

   ```bash
   brew install tfenv direnv 1password-cli
   ```

2. Hook direnv into your shell — add `eval "$(direnv hook zsh)"` to `~/.zshrc`
   (or the bash equivalent).

3. Install the pinned Terraform version — tfenv reads `infra/.terraform-version`:

   ```bash
   cd infra && tfenv install
   ```

4. Authenticate to HCP Terraform (writes `~/.terraform.d/credentials.tfrc.json`):

   ```bash
   terraform login
   ```

5. Sign in to 1Password (`op signin`), then copy the example envrc files into
   place. `.envrc` is gitignored and resolves secrets from 1Password at shell
   load. Repeat the per-environment pair for each `auth0/environments/<env>`
   you work with:

   ```bash
   cp infra/.envrc.example infra/.envrc
   cp infra/auth0/environments/<env>/.envrc.example infra/auth0/environments/<env>/.envrc
   (cd infra && direnv allow)
   (cd infra/auth0/environments/<env> && direnv allow)
   ```

If `op read` prompts for biometric unlock on every command, enable the 1Password
app's "Connect with 1Password CLI" integration (Settings → Developer).

If you don't use 1Password, export the same variables manually before running
Terraform — each `.envrc.example` lists exactly which ones its directory needs.

## Running Terraform

```bash
cd infra/<provider>/environments/<env>
terraform init
terraform plan
```

## CI

Each provider has a workflow (`.github/workflows/{auth0,render}-terraform.yml`):

- **Plan on PR** — any change under `infra/<provider>/**` posts a plan comment.
- **Manual apply** — `workflow_dispatch` with an environment + `apply` action,
  gated by a GitHub Environment (`<provider>-<env>`).

CI authenticates to HCP with a `TF_API_TOKEN` secret and to each provider with
GitHub Environment secrets (the human source-of-truth stays in 1Password).
Plan-on-PR legs fail until the Phase 1 bootstrap below has created the
workspaces, tenants, and GitHub Environment secrets they depend on.

## First-time setup

The from-scratch runbook for this repo. Terraform cannot create the things it
authenticates against, so the accounts, workspaces, tenants, and credentials in
Phase 1 are manual; Phase 2 is a checklist of what generation already filled in
and what remains; Phase 3 creates everything and pins the read-back values.

### Phase 1 — Accounts & manual bootstrap

1. **Render account** — you need a Render account/team with:
   - an **API key** (Account Settings → API Keys) and the team's **Owner ID**
     (`tea-…`/`usr-…`, visible in the dashboard URL or via the API). These
     become `RENDER_API_KEY` / `RENDER_OWNER_ID`.
   - the **Render GitHub App** installed with repository access to
     `__YURT_REPO_URL__` (Render Dashboard → Settings → Git Providers).
     Without it, service creation fails with "repository URL is invalid or
     unfetchable".
2. **HCP Terraform** — in org `__YURT_HCP_ORG__` (create the org first if it
   doesn't exist — app.terraform.io, free tier is fine), create the five
   workspaces from the table above (dashboard: New workspace → CLI-driven
   workflow). Execution mode must be **Local** (HCP holds state only; runs
   happen in CI or locally) — check Settings → Execution Mode per workspace,
   or set the org default once (org Settings → General → Default Execution
   Mode). Also create an API token for CI (`TF_API_TOKEN`): user or team
   token, Account/Team Settings → Tokens.
3. **Auth0 tenants** — create two tenants, suggested names
   `__YURT_PROJECT_SLUG__-staging` and `__YURT_PROJECT_SLUG__-production`
   (US region). The `.envrc.example` files under `auth0/environments/<env>/`
   assume those exact domains — adjust them if your tenant names or region
   differ. In **each** tenant, create a Machine-to-Machine application named
   exactly **`Terraform IaC`** (the IaC-grant module looks it up by name),
   authorized for the **Auth0 Management API** with the scope list in
   `auth0/modules/iac-grant/main.tf` (`locals.iac_management_scopes`).
   Terraform adopts and manages this grant after import (Phase 3) — it can't
   create it itself because it authenticates *as* this app (chicken-and-egg).
4. **1Password** (optional but recommended) — create a vault
   `__YURT_PROJECT_NAME__` holding:
   - `Render Terraform API Key` and `Render Terraform Owner ID` (account-level)
   - `HCP Terraform CI Token` (account-level)
   - `Auth0 Terraform IaC staging` / `Auth0 Terraform IaC production` — API
     Credential items for each tenant's M2M app (username = client_id,
     credential = client_secret)

   The `.envrc.example` files reference these names. Skipping 1Password just
   means exporting the variables by hand.
5. **Record import IDs** — Phase 3 needs three IDs from each tenant: the IaC
   grant (`cgr_…`) and the two default connections (`con_…`). Fetch them with
   a client-credentials token (repeat per tenant):

   ```bash
   DOMAIN=__YURT_PROJECT_SLUG__-<env>.us.auth0.com
   TOKEN=$(curl -sf -X POST "https://$DOMAIN/oauth/token" -H 'content-type: application/json' \
     -d "{\"client_id\":\"<Terraform IaC client_id>\",\"client_secret\":\"<Terraform IaC client_secret>\",\"audience\":\"https://$DOMAIN/api/v2/\",\"grant_type\":\"client_credentials\"}" | jq -r .access_token)
   curl -sf -H "Authorization: Bearer $TOKEN" "https://$DOMAIN/api/v2/client-grants" | jq -r '.[] | [.id, .audience] | @tsv'
   curl -sf -H "Authorization: Bearer $TOKEN" "https://$DOMAIN/api/v2/connections?fields=id,name&include_fields=true" | jq -r '.[] | [.id, .name] | @tsv'
   ```
6. **GitHub Environments** — push this repo to `__YURT_REPO_URL__` first, then
   create five GitHub Environments (repo Settings → Environments) with
   per-environment secrets (nothing is repo-level; attach required reviewers
   here if you want gated applies):
   - `render-project`, `render-staging`, `render-production`:
     `RENDER_API_KEY`, `RENDER_OWNER_ID`, `TF_API_TOKEN`
   - `auth0-staging`, `auth0-production`: `AUTH0_DOMAIN` (the tenant domain),
     `TF_AUTH0_CLIENT_ID`, `TF_AUTH0_CLIENT_SECRET` (the tenant's
     `Terraform IaC` app), `TF_API_TOKEN`

### Phase 2 — What generation filled in, and what remains

Generation substituted the HCP org, workspace names, project/display names,
repo URL, API identifier, and database names — eyeball them once, but no edits
should be needed. What remains are the values that only exist after Phase 3
creates their resources:

| Placeholder | File(s) | Pinned in |
| --- | --- | --- |
| `evm-REPLACE_ME` | `render/environments/{staging,production}/main.tf` | Phase 3 step 2 |
| `app_url = "https://REPLACE_ME.onrender.com"` | `auth0/environments/{staging,production}/main.tf` | Phase 3 step 4 |
| `cgr_REPLACE_ME` (commented import + `manage_iac_grant`) | `auth0/environments/{staging,production}/main.tf` | Phase 3 step 6 |
| `con_REPLACE_ME` (commented `connections.tf`) | `auth0/environments/{staging,production}/connections.tf` | Phase 3 step 7 |

**Lock files:** keep the committed `.terraform.lock.hcl` files exactly as-is.
They pin provider versions and carry `h1:` checksums for both platforms in
play — `darwin_arm64` (local) **and** `linux_amd64` (CI runners). A lock
regenerated by plain `terraform init` records only the current platform, so CI
init fails and versions drift. If a lock ever needs (re)generating, populate
both platforms explicitly:

```bash
terraform providers lock -platform=darwin_arm64 -platform=linux_amd64
```

### Phase 3 — Apply sequence

Run applies via Actions → "<Provider> Terraform" → Run workflow
(`gh workflow run <workflow> -f environment=<env> -f action=apply`), or locally
with `terraform apply` from the root module directory. Terraform owns
resources; the dashboard owns env-var values. Do staging first, then repeat
for production.

1. **Apply `render/project`** — creates the Render project and both
   environments; note the `evm-…` values in the `environment_ids` output.
2. **Pin the environment IDs** — replace `evm-REPLACE_ME` in
   `render/environments/<env>/main.tf` with the minted IDs; commit.
3. **Apply `render/environments/<env>`** — creates the web service, static
   site, Postgres, and env group. The first backend deploy **fails by
   design** — the env group is empty (and deploys stay red until the deploy
   branch carries current code).
4. **Pin the frontend URL** — note the `frontend_url` / `backend_url` outputs
   and set `app_url` in `auth0/environments/<env>/main.tf` to the frontend
   URL. It is usually
   `https://<slug-of-environment_name>-frontend.onrender.com` — Render only
   appends a random suffix on a name collision — but always confirm the real
   URL from the output or dashboard. Commit.
5. **Fill the backend env group** ("__YURT_PROJECT_NAME__ <Env> Backend" in
   the Render dashboard) per the
   [environment variable contract](#environment-variable-contract), then
   manually redeploy the backend; `/healthz` should go green.
6. **Apply `auth0/environments/<env>`, then adopt the IaC grant** — the first
   apply creates the API, SPA app, and post-login Action
   (`manage_iac_grant` is still `false`). Note the `spa_client_id` output.
   Then in `main.tf`: uncomment the import block, replace `cgr_REPLACE_ME`
   with the grant ID from Phase 1 step 5, flip `manage_iac_grant = true`, and
   apply again. NB: any change that both **adds IaC-grant scopes and creates
   resources needing them** takes two applies — the first run's token was
   minted before the new scopes existed, so the dependent resources 403 until
   the second.
7. **Adopt the default connections** — in `connections.tf`: uncomment every
   import and module block below the header comment (the header stays
   commented) and replace the `con_REPLACE_ME` IDs with the connection IDs
   from Phase 1 step 5 (each ID appears twice — connection + enablement).
   Apply. This enables Username-Password-Authentication for the SPA only and
   **disables google-oauth2 everywhere** (until this step, the tenant default
   leaves Google login on via Auth0's shared dev keys).
8. **Fill the static site env vars** ("__YURT_PROJECT_NAME__ <Env> Frontend")
   per the contract — `spa_client_id` from step 6 — then manually redeploy
   the frontend.
9. **Smoke check** — frontend loads, backend `/healthz` returns Ok, GraphQL
   reachable at `VITE_GRAPHQL_URL`. A login round-trip against the tenant can
   only be checked once Auth0 is wired into the app code — the scaffolded
   frontend and backend don't include it yet (see the note under the
   [environment variable contract](#environment-variable-contract)); the
   tenant, SPA app, API, and connections are ready for it.

## Adding a new environment

Same three-phase shape as first-time setup, per new `<env>`:

1. **Bootstrap (Phase 1)**: two HCP workspaces
   (`__YURT_PROJECT_SLUG__-{render,auth0}-<env>`, Local execution), an Auth0
   tenant + `Terraform IaC` M2M app, recorded import IDs, GitHub Environments
   `render-<env>` / `auth0-<env>` with secrets.
2. **Code (one PR)**: add `<env>` to the `render/project` environments map;
   copy `render/environments/staging` → `<env>` (workspace name,
   `environment_name`, placeholder `environment_id`, `branch`, db name/user);
   copy `auth0/environments/staging` → `<env>` (workspace name,
   `tenant_name`, `app_url` placeholder, `.envrc.example`; localhost in
   `additional_app_urls` belongs to staging only); add `<env>` to both
   workflows (dispatch choice + plan matrix — render's matrix entries also
   carry `dir:`); update this README's tables. Keep the copied lock file
   verbatim.
3. **Apply**: the Phase 3 sequence above.

## Custom domains

The template ships with custom domains off — services use their
`*.onrender.com` URLs. To move an environment onto your own domain:

1. **Render** — set `frontend_custom_domains` / `backend_custom_domains` in
   `render/environments/<env>/main.tf` (commented examples in place) and
   apply. DNS is not Terraform-managed: create a CNAME at your registrar for
   each hostname pointing at the service's `onrender.com` host; once it
   resolves, Render verifies the domain and auto-issues TLS.
2. **Cutover order matters** — the Auth0 apply breaks login from the previous
   origin the moment it lands, so per environment (staging first): apply the
   Render domains → create the CNAMEs → wait for **verified + certificate
   issued** on the service's Custom Domains page → then, together: update
   `app_url` in `auth0/environments/<env>/main.tf` and apply, flip the
   hostname env vars (`VITE_GRAPHQL_URL`, and any app URLs), and redeploy
   both services. Smoke-test before moving on.

### Auth0 custom domains

The Auth0 **tenants** can get custom domains too, via the `custom_domain`
variable in `auth0/environments/<env>/main.tf` (commented example in place).
Auth0 requires a credit card on file per tenant before the domain can be
created (verification only — never charged). Rollout per environment takes two
applies: set `custom_domain` and apply (creates the domain, emits the
registrar CNAME in the `custom_domain_verification_records` output) → create
that CNAME → flip `verify_custom_domain = true` and apply again (polls until
DNS resolves; the `custom_domain_status` output reaches `ready`). Tokens
issued through the custom domain carry it as issuer, so the env flips move
together: point `VITE_AUTH0_DOMAIN` (and any backend issuer URL) at the custom
domain and redeploy. Existing Auth0 sessions don't carry over to the new
domain — users log in again once, so smoke-test an existing session as well as
a fresh login.

## Environment variable contract

The variable *set* is environment-invariant; environment-specific values come
from the [per-environment values table](#per-environment-values). Extend the
table as the app grows.

Secrets are entered into the Render dashboard by hand — never into Terraform
*configuration*, and `ignore_changes = [env_vars]` keeps them out of every
plan/diff. Note the precise boundary: Terraform's refresh still reads live
values (including `DATABASE_URL`) into the HCP-encrypted state. This is
accepted: state access requires the HCP token, and that trust circle already
holds `RENDER_API_KEY`, which can read the same values from Render's API
directly — state adds no new exposure.

| Var | Where | Set by | Secret | Value / source |
| --- | --- | --- | --- | --- |
| `DATABASE_URL` | backend env group | dashboard (Phase 3 step 5) | **yes** | the environment's Database **internal** connection string (from its dashboard page) |
| `NODE_ENV` | backend env group | dashboard | no | `production` (every environment) |
| `LOG_LEVEL` | backend env group | dashboard | no | `info` |
| `GRAPHQL_PATH` | backend env group | dashboard | no | `/api/graphql` |
| `PORT` | backend runtime | Render-injected | no | — |
| `HUSKY` | backend env group | dashboard | no | `0` — skips the root `prepare` (husky) hook during Render installs |
| `SKIP_INSTALL_DEPS` | backend env group | dashboard | no | `true` — Render defaults to npm; the build command runs pnpm itself |
| `VITE_GRAPHQL_URL` | static site (build-time) | dashboard (Phase 3 step 8) | no | backend URL + `/api/graphql` |
| `VITE_AUTH0_DOMAIN` | static site (build-time) | dashboard | no | tenant domain (per-env table) |
| `VITE_AUTH0_CLIENT_ID` | static site (build-time) | dashboard | no | Terraform output `spa_client_id` |
| `VITE_AUTH0_AUDIENCE` | static site (build-time) | dashboard | no | `__YURT_API_IDENTIFIER__` |

Notes: the backend build needs `DATABASE_URL` at **build time** (`pnpm build`
runs `prisma migrate deploy`); env-group vars are available to Render builds.
`VITE_*` values are inlined into the public bundle at build time and must
never hold secrets. Auth0 is provisioned ahead of the app code: the scaffolded
**frontend** does not yet integrate Auth0 (the `VITE_AUTH0_*` vars are
consumed once `@auth0/auth0-react` is wired in), and the **backend** does not
yet validate Auth0 tokens — when backend auth is added,
`AUTH0_ISSUER_BASE_URL` / `AUTH0_AUDIENCE` join this table and
`packages/backend/src/config.ts` must validate them.

`VITE_AUTH0_AUDIENCE` must be the **same string in every environment** — it is
a logical API identifier, not a URL, and each tenant defines its own resource
server with the identical value. The post-login Action
(`auth0/modules/tenant/post-login-action.js`) hardcodes it as the claim
namespace, so a tenant provisioned with a different `api_identifier` would
silently break the stamped claims.
